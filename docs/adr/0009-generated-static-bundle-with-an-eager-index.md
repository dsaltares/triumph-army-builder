# 0009 — Serve the client a generated static bundle, eager index and lazy detail

- **Status:** Superseded by [0034](0034-reference-data-lives-in-sqlite-served-over-trpc.md)
- **Date:** 2026-09-17
- **Related:** #17, #16, #26, #50, ADR [0001](0001-snapshot-over-live-api.md)

## Context

ADR [0001](0001-snapshot-over-live-api.md) vendors the whole Meshwesh dataset into
`data/snapshot/`. That snapshot is 5.8 MB on disk, 3.4 MB minified, and every byte of it is
build-time input: it keeps `_id` sub-document keys, both the `mdText` and `htmlText` rendering of
every battle card, and 290 ally contingents no army list references.

The routes that need it want very different slices. The army index (#26) filters 656 armies by
name, keyword, date, topography and ratings, all client-side and all at once. Army detail wants one
army with its contingents, enemies and sub-faction question. The builder (#31–#35) wants troop
types and battle card metadata, and the full rules prose only when a sheet opens. Offline reading
(#50) wants all of it cached by a service worker.

Measured, gzipped, after dropping what parsing already discards:

| Slice | Raw | Gzipped |
|---|---|---|
| Army index, 656 entries | 168 KB | **24 KB** |
| One army's detail, including its contingents and enemies | — | 0.8 KB median, 2.0 KB worst |
| All 656 detail files | 2762 KB | 555 KB |
| Battle card rules prose | 68 KB | 15 KB |
| Troop types | 17 KB | 5 KB |

The index is 4% of the data and answers the first screen entirely.

## Decision

`yarn build:bundle` turns the snapshot into static JSON under `public/data/`, and `yarn build` runs
it after `yarn validate:snapshot`. The transform is `lib/data/bundle.ts`, which is pure and imports
nothing from Node, so the client can share its types and its path helpers.

One file is eager — `index.json`, holding the snapshot's source, timestamp and content hash plus
one summary per army, carrying only the fields the index route filters and sorts on. Everything
else is fetched per route: `armies/<id>.json` inlines that army's ally contingents and enemy ids so
a detail page is one request, and `troop-types.json`, `battle-cards.json`,
`battle-card-text.json` and `thematic-categories.json` back the reference and builder screens.

**The initial route's eager payload must stay under 150 KB gzipped.** `build:bundle` measures it
and fails the build over budget, so the number is enforced rather than aspired to; it is 24 KB
today. `lib/data/bundle.test.ts` asserts the same budget in the unit suite, which fails faster.

Battle card prose is split from card metadata because it is 19× its size; troop type prose is not,
because it is 4 KB and the split would buy nothing.

The bundle is generated, not committed: it is a lossless-enough function of a snapshot that is
already in git, and committing it would double every refresh diff.

## Alternatives considered

- **Ship the snapshot as-is and let the client fetch what it needs.** 3.4 MB minified, ~800 KB
  gzipped, on a phone in a club with bad wifi, to render a list of 656 names.
- **Render the index server-side and paginate.** Kills client-side filtering, which is the whole
  point of the index screen, and leaves nothing for the service worker to cache.
- **One bundle per army including shared reference data.** Removes the waterfall but re-downloads
  the troop types and battle cards with every army.
- **A tighter encoding for the index — tuples, string tables, a binary format.** Would roughly
  halve 24 KB against a 150 KB budget, in exchange for a format nobody can read in devtools.
- **Import the JSON into the page bundle instead of fetching it.** Turns data into JavaScript,
  makes it a deploy-time concern rather than a cache-time one, and blocks hydration on it.

## Consequences

- Every route pays for what it uses, and the initial route is 24 KB of data against a 150 KB
  ceiling. There is room for the index to grow — a thematic category per army, say — before anyone
  has to think about encodings.
- `public/data/` is in `.gitignore` and regenerated by `yarn dev` and `yarn build` alike, so the
  bundle cannot drift from the snapshot. The Docker image builds it in the builder stage.
- The 656 detail files are static assets, which is what makes offline caching (#50) and share
  links (#46) simple: no route handlers, no server-side data path, nothing to keep warm.
- Next.js serves `public/` with `Cache-Control: public, max-age=0` and an ETag, so every fetch
  revalidates. Once #16 stamps a data version, the bundle can move to a versioned path and be
  served immutable.
- A route that needs a new field on the index has to add it to the transform, which is where the
  budget is enforced — the cost of a field is visible at the moment it is added.
- The bundle is derived, so it is not an audit surface: a question about the data is answered
  against `data/snapshot/`, which is in git and diffable.

## Revisit trigger

The eager payload passes 100 KB gzipped, or the index screen needs a field whose cost would push it
there — at which point a compact encoding stops being premature. Also revisit if we take on a
server-side data path for any other reason, since that would make pagination cheap.
